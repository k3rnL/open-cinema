# Pi 5 8 GB cooled experimental result — 2026-08-25

Status: **partial functional pass; not a supported-platform acceptance**

This rerun replaces the failed power and cooling fixture from 2026-08-24. The
Pi completed deployment, decoder, and CamillaDSP workloads without undervoltage,
thermal throttling, or a soft-temperature event. It does not yet cover the full
TV/Bluetooth/headset scenario, live desired-graph reconciliation, rollback, or
multi-instance capacity, so the `pi5-8gb` tier remains experimental.

## PCM auto decoder result

The Pi passed 30 unit tests and two integration tests after the channel-order
fix. Focused Open Cinema processor/driver tests passed 49 tests.

Each 300-second input produced a 460,800,000-byte, 48 kHz, eight-channel
float32 output. The initial offline measurements were:

| Input | User CPU | System CPU | Wall time | Maximum RSS |
| --- | ---: | ---: | ---: | ---: |
| PCM stereo bypass | 0.58 s | 0.15 s | 0.74 s | 31,824 kB |
| AC-3 5.1 | 1.26 s | 0.14 s | 1.41 s | 34,592 kB |
| E-AC-3 5.1 | 2.10 s | 0.19 s | 3.17 s | 34,528 kB |
| DTS 5.1 | 1.84 s | 0.21 s | 12.10 s | 34,608 kB |

These are offline throughput measurements, not live latency or audible-gap
measurements. A post-fix compact AC-3 rerun completed in 14.40 seconds at 15%
CPU with 34,512 kB maximum RSS; the difference demonstrates that filesystem and
harness effects must be controlled before using wall time as a release budget.

Output inspection discovered a real channel contract error: FFmpeg supplies
packed 7.1 as `FL FR FC LFE RL RR SL SR`, while Open Cinema's public adaptive
bus is `FL FR FC LFE SL SR RL RR`. The decoder now reorders the packed result.
After the fix, AC-3, E-AC-3, and DTS all placed programme audio on channels 1–6
and left channels 7–8 silent. PCM stereo occupied channels 1–2 only.

## Unaccepted work and next measurements

This result must not promote the tier. It does not yet prove:

- physical TV input to main speakers and priority/fallback between TV and the
  accepted Bluetooth programme source;
- dynamic live codec transitions and unsupported-codec behavior;
- endpoint-switch, reconcile, processor-reconfigure, or audible-gap p95;
- a long-running capture with systematic CPU, RSS, XRUN, event-throughput,
  temperature, SQLite, Redis, and storage-write sampling;
- multiple CamillaDSP/decoder instance capacity and deterministic conflict
  behavior;
- schema-changing upgrade, coordinated rollback, restored user intent, security
  review, or rollback-window cleanup;
- an immutable coordinated release manifest and artifact provenance for all
  four source repositories.

The coordinated manifest now derives an empty PipeWire Pulse requirement from
both native processor contracts. The Pi has no installed bridge payload, active
bridge process, or Pulse runtime socket; the native 18-link graph and readiness
checks remained healthy. The same audio/readiness play then reran with
`changed=0`. This completes transport derivation and limited-live removal, but
does not complete the separate full-scenario/rollback gate for making this the
promoted default on a supported tier.

## Limited-live follow-up

The persisted limited-live graph now runs a looping debug-file source through
the native PipeWire decoder, CamillaDSP 4.1.3, and the eight-channel Wondom
output. It has passed graph disable/re-enable, individual service restarts,
PipeWire and complete service-session restarts, reboot recovery without a login,
and a controller `SIGKILL` during a partial Apply. Detailed restart and
interruption evidence is retained under `deployment/acceptance/`.

An initial steady-stream sample exposed `pcm-auto-decoder` at 100.8% CPU despite
zero PipeWire errors. Thread-level sampling isolated 100.2% CPU in the status
client serving the persistent orchestrator connection, not in audio processing.
The status writer clone made the shared Unix socket descriptor nonblocking, so
the idle reader spun on `WouldBlock`. After adding a bounded yield on the idle
read path and rebuilding the same decoder source on the Pi, a repeated ten-second
sample measured 0.9% total decoder CPU and 34,192 kB RSS. The status-client
thread measured 0.0%; all 30 unit and two integration tests passed; the graph
reconverged with 18 links. Temperature was 53.2 °C and `get_throttled` remained
`0x0` after the build, tests, restart, and live stream.

This was the initial valid single-instance PCM resource observation. Repeated
steady-state measurements follow; encoded live transitions, audible-gap
capture, and multiple-instance capacity remain separate requirements.

### Repeated steady-state live-graph measurement

The first correlated warm-up exposed a second control-plane performance defect:
the orchestrator performed an authoritative runtime capture every five seconds
as a stale-connection fallback. On the Pi, each capture consumed almost one
CPU-second, producing approximately 20% average orchestrator CPU and 97% peaks.
The runtime event contract already detects overflow and discontinuity, so the
fallback now performs a cheap WirePlumber core round-trip and reserves full
captures for startup, continuity loss, and mutation confirmation. A native
binding error-path defect found by the restart probe was also corrected so a
failed round-trip raises its intended `RuntimeError` rather than `SystemError`.

### Physical TV input and processing-latency follow-up — 2026-08-26

WirePlumber exposed the external SPDIF-to-I2S board's capture device as the
managed `TV SPDIF input`. The already-applied graph routed it through the native
decoder and CamillaDSP to the Wondom output. The user heard live TV PCM and a
movie using a supported encoded format.

An aligned PipeWire capture initially measured approximately 620 ms between the
raw TV input and CamillaDSP playback, before the USB/ALSA sink; the user perceived
about two seconds end to end. Decoder inspection found a callback-block-counted
detection window, replayed live confirmation audio, and an output callback that
filled the mapped buffer capacity instead of the current PipeWire graph cycle.

After changing detection to a 250 ms frame-counted window, dropping stale PCM
confirmation bytes, and honoring PipeWire's cycle duration, the repeated
8.021-second capture measured 64 ms at 0.9998 envelope correlation. Queue
overflow and underrun counts remained unchanged over a subsequent five-second
steady observation. The Pi passed 34 decoder unit tests, its native and status
integration tests, the coordinated contract probe, and a converged readiness
rerun. Detailed evidence is retained in
`deployment/acceptance/2026-08-26-tv-spdif-input.md`.

Final subjective lip-sync confirmation, phone-over-TV priority/fallback, the
full codec matrix, and systematic audible-gap timing remain open.
